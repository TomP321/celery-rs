# 02a — Transport: Common API + memory

Phase 2 of `PLAN.md`, part a. General objective of the phase: async transports in Rust **interoperable** with kombu (a message published by Rust is consumed by identical kombu, and vice versa; the state on the broker is what kombu expects).

This part defines the API on which 02b (Redis) and 02c (AMQP) will be implemented **in parallel** by different agents: it must be complete and stable, so subsequent parts only add one module each (`src/redis/`, `src/amqp/`) without changing the common API.

## Rust API (crate `celery-transport`)

Design a small, zero-cost API; indicatively:
- `Message { body: Bytes, content_type, content_encoding, headers: Headers, properties: Properties }` where `Headers` is an **ordered** map (preserves insertion order) of `HeaderValue` (`Null, Bool, Int(i64), BigInt(String)?, Float(f64), Str, Bytes, List, Map, Timestamp, Decimal`). Nothing `serde_json::Value`.
- `trait Transport` (async, tokyo): `declare_exchange`, `declare_queue`, `bind`, `publish`, `publish_batch`, `consume(queues, prefetch) -> stream of Delivery`, `ack`, `reject(requeue)`, `purge`, `queue_size`, `delete_queue`, `close`. Broadcast/fanout included.
- `Delivery { message, delivery_tag, exchange, routing_key, redelivered }`.
- Connection from URL with the same syntax as kombu (`redis://[:pass@]host:port/db`, `rediss://`, `amqp://user:pass@host:port/vhost`, `memory://`) and `transport_options`.
- Reconnection with backoff (same defaults as Celery's `broker_connection_retry`/`max_retries`), exposed as a configurable policy.


Required crate structure: `src/lib.rs` (`pub mod` and re-export only), `src/message.rs` (Message, Headers, HeaderValue, Properties, Delivery), `src/url.rs` (URL parsing and transport_options for all three schemes), `src/transport.rs` (traits, errors, reconnection policy), `src/routing.rs` (direct/topic/fanout virtual routing like `kombu/transport/virtual/exchange.py`, reused by memory and Redis), `src/memory.rs`. Record transports in a `connect(url)` which for `redis://`/`amqp://` returns a clear `NotImplemented` error for now: 02b and 02c will replace only that branch.

### memory

In-process transport (global registry for virtual hosts) with the same semantics as `kombu/transport/memory.py`: it is for testing and `memory://` (client and worker in the same process).


## Python bindings (in `crates/celery-py`, module `_celery_rs`)

Exposes a minimal `Connection(url, transport_options=None)` class with `publish(...)`, `declare_*`, `bind`, `drain(queues, timeout) -> list of (body: bytes, headers, properties, delivery_info, delivery_tag)`, `ack`, `reject`, `purge`, `size`, `close`. It uses a shared single-threaded tokio runtime and releases the GIL during I/O. It is used for interoperability testing and will be used by the shell in the 3. phase


The `Connection` Python class must work for any transport returned by `connect(url)`.

## Test (gate)

1. `cargo test -p celery-transport`: unit tests of message/url/routing (routing topic with `*` and `#` compared with a table of cases generated by kombu `TopicExchange.lookup`) and memory transport (publish/consume/ack/reject/requeue/prefetch/fanout/priority).
2. `crates/celery-py/tests/test_transport_memory.py` (with `.venv-ref`): same operations done with kombu `memory://` and with `_celery_rs.Connection('memory://')` produce the same messages received (body, headers, properties, delivery_info) in the same order.
3. Parsing URL: table of ≥ 30 URLs compared to `kombu.Connection(url).info()` (hostname, port, userid, password, virtual_host, transport).
